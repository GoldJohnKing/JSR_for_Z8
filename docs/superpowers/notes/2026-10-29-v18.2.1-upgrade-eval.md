# V18.2.1 升级评估（2026-10-29）

背景：上游发布 JSR V18.2.1（平铺布局 `reference/JSR_V18.2.1`，上游构建 2026-10-28）。当前集成 V18.1（载荷 manifest hash `1fd93ab0862c2064`）。本文回答：差异是什么、是否升级、收益与风险。方法与 2026-10-27-v18.1-backend-diff.md 相同（CArchive/PYZ 逐条目 SHA-256 + 手写 3.10 marshal 反汇编），反汇编器存 `/tmp/v1821cmp/`（会话临时）。

## 结论

**建议升级→已执行（2026-10-29 晚）并验证通过**。差异被上游 sanitize 报告自述为 "Only masked_alignment/masked_local scheduling; unrelated payloads byte-exact"，与我们的逐条目比对完全吻合；argv/协议/预解包契约零变化；输出与 V18.1 逐字节相同（A/B 实测，见末节）；集成面仅需 build.bat 源发现规则一处小改。收益是对齐阶段官方并行化 + 摆脱本地补丁 fork。

## 差异（三方证据：CArchive diff、PYZ diff、上游 release_sanitize_report.json）

文件级（两版 FILES-SHA256.json 1157 共同文件）仅 5 个变化：`jsr_backend.exe`（201,094,290→201,097,686 B）、`jsr_backend_manifest.json`、`jsr_traditional_3x_backend.exe`（本项目排除）、`release_sanitize_report.json`、`README.txt` + 顶层 exe 更名。**其余 1152 文件（K7 融合权重、全部 v15_2 管线模块、DLL、licenses）逐字节相同。**

CAArchive 层（各 1402 条目）仅 3 条变化：`PYZ.pyz`、'x' 条目 `wgpu\v15_2\masked_alignment.pyc`（8,113→10,676 B）、`wgpu\v15_2\masked_local.pyc`（15,468→16,073 B）。PYZ 层（各 1446 模块）仅 `v15_2.masked_alignment` 与 `v15_2.masked_local` 变化；**CLI 入口 jsr_v15_2、pipeline、masked_fit、masked_geometry_cpu、dark 全部逐字节未动**。

manifest 增 4 字段：`alignment_scheduler: bounded_ordered_frame_pool_and_shared_guide_block_rows_20261028`、`alignment_scheduler_default_threads: historical max(1,min(4,cpu_count//4)); frame memory allowance 1GiB`、`frontend_version: 18.2.1`、`traditional3x_backend_sha256`；`jsr_standalone_version` 17.3.1→18.2.1。拟合参数字段（BS192/stride128/search6/max_degree4/cap4、`stormer_spynet_used: false`）不变。

## 算法语义（反汇编实证）

拟合与数值路径未动：`BS,STRIDE,SEARCH=(192,128,6)`、residual_cap=4.0、max_degree=4、`align_pair(ref,src,rm,sm,H,ctx,pair)` 签名不变（仅新增 `block_workers` kwarg）、ValueError→identity_frame+validated_global_H 回退保留、L158 `scale = max(float(np.percentile(ref[rm],99)) if ref.any() else 0.0, 1e-06)`。

新增四个调度原语（masked_alignment）：

- `_parallel_plan(h,w,pairs)`：`threads = min(cpus, env(SRHQ_ALIGN_THREADS, max(1,min(4,cpus//4))))`；`memory_workers = max(1, 1GiB // (h*w*40))`；`frames = max(1, min(pairs, threads, memory_workers, env(SRHQ_ALIGN_WORKERS, …)))`；`blocks` 类似（`SRHQ_ALIGN_BLOCK_THREADS`）。**全幅 Z8（8280×5520）h·w·40≈1.71GiB > 1GiB → memory_workers=1 → frame_workers=1**：Z8 全部原生画幅下七帧对齐恒为「对间串行 + 每对内部 block_threads=4 块行并行」（20 核机 threads=4 全给块行）。帧级并行仅在 ≲13.4M 像素或人为放宽时启用——上游有意防全幅内存翻倍。
- `_ordered_results(solve, indices, workers)`：workers=1 **逐索引串行求解（与 V18.1 行为等价）**；workers>1 时 ThreadPoolExecutor('jsr-align-frame') + deque 有界窗口，**按提交序产出**。
- `_native_thread_guard()`：worker 内 cv2/BLAS 原生线程钉 1（threadpoolctl）。
- 块行并行（masked_local `local_measurements.<locals>.block_row`，ThreadPoolExecutor('jsr-align-row')）。

协议（stdout）：进度发射点在有序收集侧（align 的 for 循环内），`SRHQ_V12_PROGRESS|{20+15*f/N}|高光掩膜四次场对齐 f/N` 公式与 V18.1 完全相同 → **行序/单调性与 V18.1 逐行同构，E2E 单调断言零风险**；新增一行透传信息 `Alignment scheduler: N frame workers x M block threads; native threads=1`（ProtocolParser 透传未知行，兼容）。argv 契约模块逐字节未动。辅助文件 ALIGNMENT.json 新增 `parallelism` 字段。

## 输出等价性证据

2026-10-29 晚本地「帧级并行」补丁版（载荷 67adbdb…，cpu4 三连跑）backend DNG 全文件 SHA-256 三次均为 `b9f0ba7cf998…` == V18.1 串行基线（2026-10-28 确立）——**调度并行化 + 有序合并在本机实证逐字节等价**。上游 V18.2.1 同为 scheduling-only 改动（块行并行按行回填），预期同样逐字节等价；**升级验收应以一次 A/B 实测锁死**（无损组 backend DNG SHA 应 == `b9f0ba7c…`，否则以 `JSR4Z8_E2E_REGEN_BASELINES=1` 重建基线并复核差异来源）。

注：tmp_e2e/timing-out/timed.log 尾部 11:03 的 `TypeError: 'numpy.bool' object is not iterable`（载荷 2ee51a…，line 53 `max(rm.any())`）是**本地手搓补丁的 bug**——官方两版第 53 行均非该代码（官方条件为 `if ref.any()`，无内层 max）。本地补丁载荷（2ee51a…/67adbdb…）已被清理，升级官方版后全部废弃。

## 收益

1. **对齐阶段提速（官方并行化）**：V18.1 全幅对齐 58.5~74s（占比 ~15%）。块行并行 4 线程预期 1.5~2.5×（本机 cpu4 实验显示纯 CPU 并行争用显著，官方 threadpool_limits 钉 1 方案优于补丁实验的无限制形态，但确切加速比需实测）。端到端预期省 ~20~50s/组（394→~345~375s，5~13%）；Transformer 75.3% 占比不变，Amdahl 上限 −15%。
2. **回归上游原样，废弃本地 fork**：10-28 GPU 移植评估的「性价比 a（6 对并行）需 fork 违反上游原样约定」顾虑被上游官方实现直接消除；两枚实验载荷与手搓补丁维护负担清零。
3. **质量零回归**：拟合参数/算法/输出哈希等价证据充分；黑场/PTC/argv 标定链完全不受影响。
4. **可调性**：SRHQ_ALIGN_* 环境变量为未来调优留口（本项目默认不设，用上游默认）。

## 集成改动面（已落地）

- **build.bat（唯一必改项，已改）**：源发现只认 `JSR_V*\JSR_V*_Sharp` 嵌套与 `Jiangtherapee-Bridge-*` 平铺，不认 V18.2.1 的 `JSR_V*` 平铺布局。改法：JSR_V* 目录（/o-n 降序）内先探 `_Sharp` 嵌套、再探平铺 `resources\jsr_backend.exe`，首个命中即定（V18.2.1 > V18.1，胜出）。
- PayloadPacker 版本正则 `^(?:Jiangtherapee-Bridge-|JSR_V)(\d+(?:\.\d+){1,3})` 对平铺目录名 `JSR_V18.2.1` 解析为 18.2.1 ✓（实跑验证）；排除清单无需增（两版文件集相同，traditional3x 已排除）；EnginePreextractor b+x 落盘规则不变（'x' 条目仍存在）；UI 版本行自动显示 v18.2.1（manifest backendVersion 实证）。
- 验收：全量单测（318）+ build.bat + `--selftest` + A/B 计时与哈希终验全部通过（见上节）。

## 风险

| 风险 | 等级 | 依据/对策 |
|---|---|---|
| 输出漂移 | 低 | 上游 scheduling-only 自述+本地帧并行逐字节实证；A/B 终验锁死；不等价则重建基线 |
| 协议变化 | 极低 | 进度公式/发射点逐行同构（反汇编）；新增行透传兼容 |
| 端到端提速不及预期 | 中 | cpu4 实验显示本机并行争用重；即便 0 收益也无回退（其余 1152 文件同 V18.1） |
| build.bat 发现规则改动引入回归 | 低 | 现有 V18.1 嵌套树仍在，规则向后兼容；pack-payload manifest 哈希自决换入 |
